# 백엔드 수정 요청서 — 예약 preview 첫 슬롯 시작 시각 변경

작성일: 2026-10-28 · 대상: 예약 API 백엔드 담당자 · 우선순위: 높음

## 1. 요청 요약

오후 예약 5개를 전송했지만 `POST /api/v1/rental-previews`가 **0번 슬롯의 시작만 과거로 이동**시켜 여러 날의 연속 대여로 반환합니다. 나머지 1~4번 슬롯과 모든 종료 시각은 정상입니다. 확장된 0번 슬롯이 선택하지 않은 오전 예약과 겹쳐 `SLOT_CONFLICT` 5건이 발생했습니다.

**수정 요청:** 명시적으로 보낸 `slots`의 실제 사용 구간을 보존하고, 그 구간으로 충돌을 검사해 주세요. 준비 작업의 실행 예정 시각이나 현재 시각을 사용자 대여 시작 시각에 덮어쓰지 않아야 합니다.

자료는 사용자가 전달한 Payload와 최신 preview 응답을 전사·정리한 것입니다. 원본 HAR, HTTP 상태, X-Request-Id, 실행 중인 백엔드 커밋은 확보하지 못했습니다. 수정 전 동일 요청의 서버 로그와 배포 버전을 대조해 주세요. 아래 분석은 최초 스크린샷이나 앞선 다른 응답이 아닌 **이번 최신 5개 슬롯 응답** 기준입니다.

## 2. 재현 요청

- 엔드포인트: `POST /api/v1/rental-previews`
- 서버: `serverId=57` — 화면 표시명 ‘대여 컴퓨터 001’
- 선택: 2026-11-01~2026-11-05, 매일 오후 16:00~23:00, 한국 시간
- 방식: 연속 장기 대여가 아닌 **날짜별 5개 슬롯**

```json

  "purpose": "ㅇㅇ",
  "slots": [
    {
      "startAt": "2026-11-01T16:00:00+09:00",
      "endAt": "2026-11-01T23:00:00+09:00"
    },
    {
      "startAt": "2026-11-02T16:00:00+09:00",
      "endAt": "2026-11-02T23:00:00+09:00"
    },
    {
      "startAt": "2026-11-03T16:00:00+09:00",
      "endAt": "2026-11-03T23:00:00+09:00"
    },
    {
      "startAt": "2026-11-04T16:00:00+09:00",
      "endAt": "2026-11-04T23:00:00+09:00"
```

## 3. 요청과 응답 슬롯 매칭

`+09:00`과 `Z`는 같은 시점을 표현할 수 있으므로 문자열 자체가 아니라 UTC 시점으로 비교했습니다.

| 인덱스 | 요청 사용 시간(KST) | 기대 시작(UTC) | 실제 응답 시작(UTC) | 종료 일치 | 결과 |
| --- | --- | --- | --- | --- | --- |
| 0 | 11-01 16:00~23:00 | 2026-11-01T07:00:00Z | 2026-10-28T00:28:03.152263Z | 일치 | **시작 시각 불일치** |
| 1 | 11-02 16:00~23:00 | 2026-11-02T07:00:00Z | 2026-11-02T07:00:00Z | 일치 | 정상 |
| 2 | 11-03 16:00~23:00 | 2026-11-03T07:00:00Z | 2026-11-03T07:00:00Z | 일치 | 정상 |
| 3 | 11-04 16:00~23:00 | 2026-11-04T07:00:00Z | 2026-11-04T07:00:00Z | 일치 | 정상 |
| 4 | 11-05 16:00~23:00 | 2026-11-05T07:00:00Z | 2026-11-05T07:00:00Z | 일치 | 정상 |

0번 슬롯 상세:

| 항목 | 한국 시간(KST) |
| --- | --- |
| 요청 시작 | 2026-11-01 16:00:00 |
| 응답 시작 | **2026-10-28 09:28:03.152263** |
| 요청·응답 종료 | 2026-11-01 23:00:00 |

즉, `11/01 16:00~23:00`이어야 할 0번 슬롯이 `10/28 09:28:03.152263~11/01 23:00`으로 확장됐습니다. 단순한 UTC/한국 시간 변환 차이가 아닙니다. 앞선 응답의 `00:26:43.141354Z`와 달리 이번에는 `00:28:03.152263Z`로 바뀌었습니다. 시작을 현재 시각으로 치환하는 분기가 있는지는 **확인 후보이며 아직 원인으로 확정하지 않았습니다.**

## 4. 최신 preview에서 발생한 충돌

반환된 공통 값:

```json
{
  "serverId": 57,
  "minimumSwitchSeconds": 3600,
  "serverAvailable": true,
  "canReserve": false,
  "horizonPolicy": "CALENDAR_TWO_MONTHS"
}
```

5건의 `conflicts[].candidate`는 모두 잘못 확장된 0번 슬롯과 같습니다.

| 충돌 인덱스 | blockedStart(KST) | blockedEnd(KST) | 코드 |
| --- | --- | --- | --- |
| 0 | 2026-10-27 23:58:01.274170 | 2026-10-28 15:00:00 | SLOT_CONFLICT |
| 1 | 2026-10-29 08:00:00 | 2026-10-29 15:00:00 | SLOT_CONFLICT |
| 2 | 2026-10-30 08:00:00 | 2026-10-30 15:00:00 | SLOT_CONFLICT |
| 3 | 2026-10-31 08:00:00 | 2026-10-31 15:00:00 | SLOT_CONFLICT |
| 4 | 2026-11-01 08:00:00 | 2026-11-01 15:00:00 | SLOT_CONFLICT |

확장된 candidate 기준으로는 위 5건의 겹침 판정이 맞습니다. 문제는 **충돌 검사에 들어간 candidate가 사용자가 보낸 시간과 다르다는 것**입니다.

원래 요청한 첫 슬롯은 11/01 16:00 시작이고 같은 날 오전 차단은 15:00 종료입니다. `minimumSwitchSeconds=3600`이면 정확히 60분 간격이므로 허용되어야 합니다. 10/28~10/31의 차단 구간도 원래 요청보다 앞에 있어 겹치지 않습니다. 전송된 원래 슬롯 5개는 제공된 차단 구간 5개와 중복·전환 시간 부족이 없음을 오프라인 비교로 확인했습니다.

`serverAvailable=true`는 서버 이용 가능 상태를 뜻하므로 이것만으로 예약 승인 여부를 판단하지 않습니다. 이번에는 응답 내부의 슬롯 변형이 핵심입니다.

## 5. 백엔드 확인·수정 범위

1. 동일 요청의 수신 직후 원본 slots, 정규화 후 slots, 충돌 검사 candidate, 응답 slots를 X-Request-Id로 연결해 기록·대조해 주세요. 비밀번호·토큰은 로그에 남길 필요가 없습니다.
2. 실제 배포 버전의 `ReservationCompiler.compile()`과 그 전후 서비스에서 첫 슬롯만 처리하는 분기를 우선 확인해 주세요. 현재 시각 보정, 즉시 시작 처리, `getFirst()`/0번 요소 변경, 공유·재사용하는 mutable 리스트, 테스트용 시간 보정은 확인 후보입니다.
3. `PREPARE` 등의 작업 실행 예정 시각은 실제 대여 startAt과 별도로 관리해 주세요. 준비를 먼저 실행하더라도 사용자가 선택한 미래 슬롯을 현재 시각부터의 연속 대여로 바꾸지 않아야 합니다.
4. 정규화는 같은 시점의 UTC 표현, 정렬, 실제 겹침·맞닿음 등 사용 시간 합집합을 보존하는 처리로 제한해 주세요. 오후 슬롯 사이의 오전·야간 공백을 임의로 채우면 안 됩니다. 명시적인 장기 대여는 사용자가 보낸 연속 구간을 그대로 검사합니다.
5. `RentalService.preview()`와 `RentalService.create()`가 동일한 슬롯 정규화·충돌 정책을 사용하도록 확인해 주세요. preview만 수정하고 실제 생성 단계에서 다시 확장하는 문제가 없어야 합니다.
6. 전환 시간 미달은 `< minimumSwitchSeconds`로 판단하고, 정확히 3,600초인 간격은 허용해 주세요. 이번 문제를 우회하려고 전환 시간을 0으로 바꾸거나 정상적인 충돌 검사를 제거하는 수정은 필요하지 않습니다.

참고: 확인했던 로컬 전달본의 `ReservationCompiler.compile()`은 명시적 slots를 가져온 후 정렬·병합합니다. 이번처럼 미래 시작을 10월 28일 시각으로 확장하는 명시적 로직은 해당 전달본에서 확인하지 못했습니다. **수정 전 실제 실행 중인 소스·브랜치·빌드가 전달본과 같은지 먼저 확인해 주세요.**

## 6. 기대 결과

아래는 제공된 5개 차단 구간 외에 추가 충돌·별도 예약 제한이 없다는 조건의 기대 예시입니다. 실제 DB의 다른 예약까지 없다는 뜻은 아닙니다.

```json
{
  "serverId": 57,
  "minimumSwitchSeconds": 3600,
  "serverAvailable": true,
  "canReserve": true,
  "horizonPolicy": "CALENDAR_TWO_MONTHS",
  "slots": [
    {
      "startAt": "2026-11-01T07:00:00Z",
      "endAt": "2026-11-01T14:00:00Z"
    },
    {
      "startAt": "2026-11-02T07:00:00Z",
      "endAt": "2026-11-02T14:00:00Z"
    },
    {
      "startAt": "2026-11-03T07:00:00Z",
      "endAt": "2026-11-03T14:00:00Z"
    },
    {
      "startAt": "2026-11-04T07:00:00Z",
      "endAt": "2026-11-04T14:00:00Z"
    },
    {
      "startAt": "2026-11-05T07:00:00Z",
      "endAt": "2026-11-05T14:00:00Z"
    }
  ],
  "conflicts": []
}
```

- 0번 시작은 `2026-11-01T07:00:00Z`여야 합니다.
- slots 수는 5개이고 각 날짜의 실제 사용 구간은 요청과 같아야 합니다.
- 위 재현 조건에서는 `conflicts=[]`, `canReserve=true`여야 합니다.
- 다른 실제 예약이 있다면 요청한 오후 슬롯 중 해당 구간만 충돌로 반환해야 합니다.

## 7. 회귀 테스트·완료 기준

| 사례 | 기대 결과 |
| --- | --- |
| 이번 요청 + 제공된 차단 구간 5개 | 요청 슬롯 보존, 충돌 없음 |
| 미래 날짜의 오후 1일 예약 | 시작을 현재 시각으로 바꾸지 않음 |
| 같은 기간에 매일 오전 08~15 예약 + 오후 16~23 신청 | 준비 시간 3,600초이면 허용 |
| 첫 슬롯뿐 아니라 중간·마지막 슬롯에 실제 오후 중복 | 해당 candidate로 거절 |
| 전환 간격 정확히 3,600초 / 그보다 짧음 | 각각 허용 / INSUFFICIENT_SWITCH_TIME |
| UTC와 +09:00으로 동일 시간 전송 | 같은 예약·충돌 결과 |
| 명시적 연속 장기 대여 | 연속 구간을 보존하고 실제 중복 거절 |
| 과거 시작 시각 입력 | 합의된 과거 예약 정책에 따라 명시적 오류; 조용히 다른 시간으로 변경하지 않음 |
| preview 승인 후 실제 예약 생성 | 저장된 slots도 요청과 같은 실제 사용 구간 |

완료 회신에는 적용 커밋·배포 버전, 동일 요청의 수정 전후 slots 및 conflicts, 서버 테스트 결과, X-Request-Id를 포함해 주세요. 실제 예약 생성 검사는 개발·테스트 환경에서 수행해 주세요.

## 8. 프론트 반영 상태

프론트는 이미 요청 slots와 preview slots의 실제 사용 구간을 비교하고, 다르면 신청을 중단해 선택하지 않은 시간의 예약 생성을 막습니다. 충돌 시 candidate와 차단 구간을 한국 시간으로 안내합니다.

`PREVIEW_SLOT_MISMATCH`는 **프론트 내부 오류 코드**입니다. 서버가 반환한 신규 오류 코드나 백엔드 HTTP 502가 아니며, 이번 문서는 백엔드에 이 코드를 새로 구현해 달라는 요청이 아닙니다. 프론트의 방어 처리만으로 실제 백엔드 슬롯 변경 문제가 해결된 것은 아닙니다.
