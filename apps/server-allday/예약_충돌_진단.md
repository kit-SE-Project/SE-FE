## 확인한 현상

사용자가 서버 ‘대여 컴퓨터 001’에서 2026-10-28~2026-10-31, 매일 오후 16:00~23:00 신청 시 ‘선택한 기간에 다른 예약과 충돌합니다’ 안내를 받았다. 브라우저 제어 도구는 Whale 창 바인딩 오류로 두 번 실패했고, 이후 사용자가 실제 요청·응답을 제공했다.

## 사용자가 전달한 요청·응답

- 요청: serverId=57, 2026-11-01~2026-11-05의 매일 오후 16:00~23:00, 날짜별 5개 slots. 프론트의 전송 본문은 오후 시간대로 구성되어 있다.
- 응답: canReserve=false, serverAvailable=true, minimumSwitchSeconds=3600. 첫 slots 항목은 `2026-10-28T00:26:43.141354Z`~`2026-11-02T14:00:00Z`이다. 한국 시간으로 10월 28일 09:26부터 11월 2일 23:00까지 연속 구간이며, 이후 11월 3~4일의 오후 슬롯 두 개가 있다.
- conflicts는 이 첫 연속 구간과 10월 28일~11월 2일 오전 예약·차단 구간의 실제 겹침을 반환한다. 예를 들어 10월 29일의 blockedStart/blockedEnd는 한국 시간 08:00~15:00이다.
- 따라서 응답의 candidate 기준으로는 충돌이 맞지만, 사용자가 선택·전송한 오후 슬롯과 응답의 검사 구간이 다르다. 날짜 범위도 요청은 11월 1~5일, 응답은 10월 28일~11월 4일로 다르므로 동일 Network 요청의 Payload/Response인지 확인해야 한다. 동일 요청이면 실행 중인 백엔드의 슬롯 변환 또는 응답 매칭 문제다. 제공받은 로컬 백엔드 소스만으로 실제 배포 코드를 수정했다고 판단하지 않는다.

## 코드로 확인된 동작

- 프론트는 오후 4일을 연속 구간 하나가 아닌 날짜별 4개 슬롯으로 전송한다.
- 매일 오전 08:00~15:00 예약과 오후 16:00~23:00 신청은 전환 준비 시간이 3,600초이면 허용된다. 경계값 및 여러 날짜 비교 회귀 테스트로 확인했다.
- 달력의 예약 표시는 실제 startAt/endAt을 기준으로 한다. 예약 검사에서는 서버가 제공한 blockedStart/blockedEnd와 minimumSwitchSeconds도 반영한다. 따라서 실제 차단 구간이 다르면 달력 표시만으로 충돌을 판단할 수 없다.
- 기존 App.jsx는 canReserve 누락 등 잘못된 응답도 단순 충돌로 표시했다. 이제 응답 형식 오류·서버 이용 불가·예약 중복·전환 시간 부족을 구분한다.
- 사전검사 거절 시 해당 candidate와 blockedStart/blockedEnd를 한국 시간으로 안내하고 예약 가능 시간 재조회 버튼을 제공한다. 서버가 거절한 예약을 강제로 생성하지 않는다.
- 사전검사 slots와 프론트 요청 slots의 실제 사용 구간이 다르면 PREVIEW_SLOT_MISMATCH로 신청을 중단한다. UTC/한국 시간 표현 차이 및 맞닿은 슬롯의 동등한 병합은 허용하지만, 선택하지 않은 오전·야간·날짜가 추가되는 변환은 허용하지 않는다.

## 실제 원인 확정에 필요한 자료

같은 Network 요청임을 확인한 뒤 다음 값을 함께 비교한다. 토큰·비밀번호·Authorization 헤더는 필요 없다.

1. POST /api/v1/rental-previews 응답의 canReserve, serverAvailable, minimumSwitchSeconds, conflicts 및 slots.
2. GET /api/v1/servers/{id}/availability 응답의 blockedSlots.
3. 가능하면 응답의 X-Request-Id와 실행 중인 백엔드 버전.

서버 사전검사의 conflicts[].candidate와 blockedStart/blockedEnd를 대조해 실제 오후 예약, 오전 예약의 차단 구간 연장, 전환 시간 미달, 가용 시간 조회 이후 추가된 예약, 응답 계약 불일치 중 어느 경우인지 확인한다. 제공받은 Desktop 백엔드 소스와 실제 배포 소스가 같은 버전인지는 확인되지 않았다.
