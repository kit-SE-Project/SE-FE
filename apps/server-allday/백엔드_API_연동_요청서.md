# Server Allday 백엔드 API 연동 요청서

> **0.5.0 전달 후 상태 (2026-10-14):** 아래 본문은 0.2.0을 기준으로 작성했던 요청 기록입니다. 새 전달본에 폼 로그인·JWT 갱신·로그아웃, 서버 메타데이터 수정·논리 삭제, 서버 시각·예약 한도, 대여 사양 snapshot이 포함되어 프론트에 반영했습니다. 현재 동작은 `API_AUDIT.md`, `LOGIN.md`를 참고하세요. 실제 운영 SEBoard/SSO와 물리 장비 통합은 여전히 별도 확인 대상입니다.

작성일: 2026-10-14  
대상: 백엔드 개발 담당자  
기준: `server-allday-backend/docs/API_계약.md`, `docs/openapi.json` 0.2.0 및 현재 컨트롤러·예약 서비스 구현

## 요청 목적

서버 대여 프론트엔드의 실 서비스 연결을 위해 정식 인증 계약과 관리자 서버 정보 수정·삭제 API를 확정해 주세요. 프론트는 현재 공개 명세의 개발 사용자 Bearer 토큰 인증과 기존 대여 API를 사용하도록 수정했습니다. 서버가 아직 배포되지 않아 실제 인증·DB·VM 동작은 검증하지 않았습니다.

아래 **제안**으로 표시한 경로·필드·오류 코드는 현행 API에 존재한다는 뜻이 아닙니다. 백엔드와 합의한 후 OpenAPI에 반영하고 프론트를 연결할 예정입니다.

| --- | --- | --- | --- |

| 높음 | 서버 등록 정보 삭제 API | 현행 명세에 없음 | 삭제 경로, 진행 대여 차단, 기록 보존 정책 |

## 1. 정식 로그인 및 사용자 권한

현행 프론트의 **명세 API** 모드는 발급받은 개발 사용자 토큰을 `Authorization: Bearer ...`로 보내고 `GET /api/v1/me`로 신원을 확인합니다. 응답 `{ "memberId": 1001, "role": "STUDENT" }` 또는 `ADMIN`을 기준으로 관리자 화면을 표시합니다. 토큰을 브라우저 영구 저장소에 저장하지 않습니다.

아이디·비밀번호 기반 실 서비스 로그인에 사용할 아래 계약을 제공해 주세요.

- 학과 계정/SEBoard 인증을 직접 사용하는지, 별도 인증 API 또는 SSO를 사용하는지와 로그인 흐름.
- 인증 요청 경로·메서드·Content-Type·필드 및 성공 응답 전체 예시.
- access token/쿠키의 저장·전송 방법, 유효 기간, 갱신 방법, 로그아웃 및 폐기 방법.
- `/api/v1/me`의 `memberId`와 역할 정의 유지 여부. 관리자 권한은 서버에서 결정하고 관리자 요청에 반드시 권한 검사를 수행.
- 로그인 실패, 만료, 권한 부족의 HTTP 상태 및 오류 본문. 일반적으로 인증 실패는 401, 권한 부족은 403으로 구분 요청.
- 쿠키 인증을 채택하면 CORS credentials·SameSite·CSRF 정책도 함께 제공.

**경로 제안(합의 필요):** `POST /api/v1/auth/login`, `/auth/refresh`, `/auth/logout`. 경로를 먼저 확정하기 위한 예시이며 프론트는 이 경로들을 호출하지 않습니다. 기존 학과 인증 계약을 사용하는 경우 그 명세를 제공해 주세요.

프론트의 로컬 로그인과 발표용 인증 어댑터는 제거했습니다. `/formLogin`, `/mypage`, `/refresh`, `/logoutProc`는 현행 0.2.0 명세에 없으므로 호출하지 않습니다. 학과의 기존 인증 경로를 실 서비스에 사용할 경우 별도 명세와 실제 응답을 제공해 주세요.

개발 검증용 사용자·관리자 토큰은 별도로 전달해 주세요. 본 문서나 공개 저장소에는 실제 토큰을 넣지 않습니다. 사용자 SSH 공개키 입력·선택·관리 API와 화면은 서비스 범위에서 제외합니다.

## 2. 관리자 서버 정보 수정

목적: 관리자가 서버를 선택해 서버명, CPU, 메모리, GPU, 카테고리를 바꾸고 저장된 결과를 목록에서 즉시 확인.

**제안:** `PATCH /api/v1/admin/servers/{id}`

```json
{
  "expectedVersion": 3,
  "displayName": "SE-Server-01",
  "categoryId": 1,
  "cpuModel": "Intel Xeon E5-2680 v4 · 28c",
  "memoryGb": 128,
  "gpuModel": "RTX 3090 x2",
  "reason": "장비 사양 정보 갱신"
}
```

위 예시는 저장할 전체 편집 값을 보내는 방식입니다. 생략 필드 및 null 처리 방식을 명세에 정의해 주세요. 등록 시 필요한 `nodeName`은 물리 관리 노드 식별자이므로 이 화면의 정보 수정에서는 변경하지 않는 방향을 제안합니다.

요청 사항:

- ADMIN만 접근. 서버 존재 여부 및 `expectedVersion`을 확인하고 저장 시 version 증가.
- 기존 등록 입력의 제약과 일관되게 검증: 서버명 필수·100자 이내, 유효 카테고리, CPU/GPU 각각 200자 이내, 메모리 양의 정수. GPU 없음의 null/문자열 표현과 이름 중복 허용 여부 확정.
- 대여 진행 중 표시명 변경, 카테고리 변경, 장비 사양 변경의 허용 여부를 구분하여 명시. 실제 VM 자원 변경이 필요한 경우 별도 작업으로 처리.
- 성공 200 응답에 최신 서버 모델(`id`, `version`, 사양, `categoryId`, 상태, `reservationAllowed`)을 반환하거나, 저장 후 조회하는 방식을 명확히 지정.
- 없는 서버 404, 권한 부족 403, 입력 오류 및 카테고리 오류, version 충돌 409를 일관된 오류 본문으로 반환.
- 상태 변경과 메타데이터 변경이 같은 version을 공유하는지, 멱등 키를 요구하는지 확정.

프론트는 서버 목록의 선택 강조를 제공하지만, 서버 정보 수정 API가 확정될 때까지 수정 버튼을 비활성화합니다. 임시 저장 처리는 제거했으며 API 확정 후 수정 폼과 저장 처리를 연결할 예정입니다.

## 3. 관리자 서버 등록 정보 삭제

목적: 관리자에게 서버명·사양·카테고리를 확인시키고 승인한 경우에만 목록에서 제거. 삭제는 서버 등록 정보의 비활성화를 의미하도록 제안하며 물리 서버나 VM 삭제 작업을 이 API에 묶지 않습니다.

**제안:** `DELETE /api/v1/admin/servers/{id}`  
`Idempotency-Key` 헤더 및 아래 본문 예시:

```json
{
  "expectedVersion": 3,
  "reason": "대여 장비 운영 종료"
}
```

DELETE 본문을 지원하지 않는 환경이면 `POST .../{id}/deactivate` 등의 명시적인 대안을 확정해 주세요. 이 예시를 현재 지원 경로로 사용하지 않습니다.

요청 사항:

- ADMIN·존재 여부·version 검사. `RESERVED`, `PROVISIONING`, `READY`, `ACTIVE`, `RETAINED`, `RETURNING` 등 종료되지 않은 계약이 있으면 삭제 거절. 거절 기준을 계약 상태별로 명세화.
- 진행 중 계약은 409 `SERVER_IN_USE` 등 구분 가능한 오류 코드로 반환하는 방향 제안. version 충돌 오류도 별도 코드로 구분.
- 과거 대여 기록의 서버 ID·표시명·사양·GPU 정보 보존. 참조를 끊는 물리 삭제보다 논리 삭제 권장. 기존 기록 조회·내 대여 현황에 영향이 없어야 함.
- 삭제 성공은 204로 제안. 이후 서버 목록·가용 시간·신규 예약 대상에서 제외하고, 같은 멱등 키 재시도 및 이미 삭제된 ID의 처리 방식 정의.
- 삭제와 신규 예약이 동시에 발생해도 종료되지 않은 계약을 가진 서버가 삭제되지 않도록 트랜잭션 수준에서 보장.

프론트의 로컬 삭제 처리와 확인 모달은 제거했습니다. 삭제 버튼은 계약 확정 전까지 비활성화하며, API 제공 후 대상 확인·취소·성공·실패 흐름을 연결할 예정입니다.

## 4. 예약·장기 대여 정책 확인

프론트는 명세에 없는 `LONG_TERM` 값을 요청에 추가하지 않습니다. 오전/오후는 매일 개별 `slots`, 장기 대여는 하나의 연속 슬롯을 전송합니다.

```json
{
  "serverId": 1,
  "purpose": "장기 학습 실험",
  "slots": [
    { "startAt": "2026-10-20T00:00:00+09:00", "endAt": "2026-10-23T00:00:00+09:00" }
  ]
}
```

이 예시는 10월 20~22일의 24시간 연속 사용입니다. 장기 대여 동안 야간에도 VM·접속이 유지되는지, 최대 기간 및 재신청 정책을 확인해 주세요. 장기 일정은 달력에서 보라색 원으로 표시합니다.

현행 구현에 맞춘 프론트 수정 사항:

- `availability.minimumSwitchSeconds`를 읽고 기존 예약 앞·뒤의 최소 간격을 검사. 간격이 정확히 최소값이면 허용.
- `blockedStart`/`blockedEnd`를 충돌 범위로 사용하고 실제 예약 시간과 전환 여유 시간을 시각적으로 구분.
- 한국 시간 기준 현재 시각에 2개월을 더한 **정확한 종료 한도** 검사. 월말에는 마지막 날짜로 보정. 날짜만 비교하지 않음.
- 미리보기 또는 신청에서 예약 충돌·전환 시간 부족이 반환되면 가용 시간 재조회.

서버와 사용자 기기의 시계 차이를 줄이기 위해 `availability`에 `serverNow`, `reservationHorizonAt`을 추가하는 방안을 검토해 주세요. **선택 제안 필드이며 현재 프론트에서 사용하지 않습니다.** 현재 최종 예약 판단은 서버의 미리보기·신청 응답을 따릅니다.

## 5. 배포 및 명세 전달

다음을 함께 전달해 주세요.

1. 확정된 OpenAPI 파일과 변경 내역, 요청·성공·실패 응답 예시. 요청 ID 및 기존 `{code, message, requestId}` 오류 형식 유지 여부.
2. 개발/운영 API 기본 주소, HTTPS 및 접근 방법. 현행 명세 기본 주소는 `http://127.0.0.1:18080`.
3. 실제 프론트 출처에 맞는 CORS 설정. `http://localhost:3000`, `http://127.0.0.1:3000`, `http://127.0.0.1:3001`은 서로 다른 출처. 사용할 출처만 명시적으로 허용하고 Authorization·Content-Type·Idempotency-Key 헤더 및 PATCH/DELETE preflight 지원 확인.
4. 본문/헤더 요청 ID를 쓰는 경우 브라우저가 읽을 `Access-Control-Expose-Headers` 설정.
5. STUDENT/ADMIN 검증용 계정·토큰, 테스트 서버·카테고리, 가용/점검/오류/반납 상태 데이터. 실제 VM 접속을 제공하는 환경과 시뮬레이션 환경의 구분.

## 연동 완료 기준

| 확인 항목 | 기대 결과 |
| --- | --- |
| 로그인·만료 | 정상 신원 반환, 잘못된 인증 401, 만료 처리·갱신·로그아웃 정책대로 동작 |
| 관리자 권한 | STUDENT의 관리자 API 직접 호출 403, ADMIN만 수정·삭제 성공 |
| 수정 | 이름·사양·분류 저장 후 재조회 일치, 잘못된 값 거절, 오래된 version 409 |
| 삭제 | 확인 후 목록 제외, 진행 대여 시 거절, 과거 기록 보존, 동시 예약 안전성 |
| 재시도 | 응답 유실 후 멱등 재시도가 중복 예약·등록·삭제를 만들지 않음 |
| 예약 경계 | 최소 간격 미달 거절·정확한 간격 허용, 월말·정확한 2개월 시각 한도 검사 |
| 장기 대여 | 자정~마지막 날 다음 자정 연속 슬롯, 야간 접속 유지, 단기 슬롯과 충돌 검사 |
| 브라우저 연결 | 허용 출처의 preflight·API 응답 성공, 오류 및 요청 ID 표시 |
| 실제 대여 | RESERVED를 즉시 사용 가능으로 표시하지 않고 실제 상태와 `connection.available`에 따라 접속 표시 |

## 프론트에서 완료한 조치

명세 토큰 클라이언트를 실제 화면에 연결하고 로컬 로그인·목업 JSON·발표용 인증·가상 VM 진행·가짜 접속 정보는 제거했습니다. HTTP 401 상태 전달·세션 정리, 비 JSON 오류 안내, 예약 전환 간격·정확한 종료 시각 검증을 수정했습니다. 모든 서비스 데이터는 API에서 조회하며 API 실패 시 오류를 표시합니다.

현재 API·예약·서버 입력 테스트 24개와 웹 빌드로 변경 사항을 검증합니다. 이는 요청 생성과 경계 검증이며 배포 서버 인증·DB 저장·worker·VM·SSH 전체 흐름의 실제 성공을 의미하지 않습니다. 최종 실행 결과는 `API_AUDIT.md`, `VERIFICATION.md`에 있습니다.
