## 사용 계약

인증은 해당 백엔드 문서의 Bearer access 토큰이며, 관리자 카테고리 API에는 서버에서 확인한 `ROLE_ADMIN`이 필요하다. 프론트에서 역할을 임의 지정하지 않는다.

| 동작 | 메서드·경로 | 요청 본문 | 성공 |
| --- | --- | --- | --- |
| 관리자 전체 목록 | `GET /api/v1/admin/categories` | 없음 | 200, 카테고리 배열 |
| 등록 | `POST /api/v1/admin/categories` | name, description | 201, 카테고리 객체 |
| 수정 | `PATCH /api/v1/admin/categories/{id}` | name, description, expectedVersion | 200, 갱신 객체 |
| 삭제 | `DELETE /api/v1/admin/categories/{id}` | expectedVersion | 204, 빈 본문 |

카테고리 객체는 `{id, name, description, version}`이다. 이름은 필수·100자 이하, 설명은 선택·2,000자 이하이고 null/빈 값으로 삭제할 수 있다. 프론트는 입력을 trim하고 빈 설명은 null로 전송한다. PATCH는 전체 값을 덮어쓰므로 설명을 변경하지 않아도 기존 설명을 함께 보낸다. 수정·삭제는 목록에서 받은 0 이상의 정수 version을 사용한다.

등록·수정·삭제 모두 `Idempotency-Key`를 전송한다. 같은 요청을 통신 실패 후 재시도할 때 같은 본문·키를 유지하고, 작업 종류·대상·버전·본문이 달라지면 별도 시도로 구분한다.

`IDEMPOTENCY_KEY_REUSED`(422)가 확정 응답으로 오면 실패 사유를 표시하고 해당 키를 폐기한다. 사용자가 다시 저장/삭제 확인을 누르면 새 키로 요청한다. 통신 실패처럼 처리 결과가 불명확할 때는 키를 임의 교체하지 않는다.

관리자 목록은 서버가 아직 배정되지 않은 카테고리도 포함한다. 일반 `GET /api/v1/categories`는 백엔드의 실제 장비 모드에 따라 서버가 배정된 분류만 반환할 수 있다. 따라서 새 분류가 관리자·서버 편집 목록에는 보이지만 대여 화면에는 아직 나타나지 않는 것이 가능하다.

## 프론트 반영

- 기존 `src/api.js`의 관리자 카테고리 4개 호출은 확인한 컨트롤러와 일치하여 경로·본문을 임의 변경하지 않았다.
- 추가·수정·삭제 성공 문구를 표시하고 실제 목록을 재조회한다. 저장 성공 뒤 조회가 실패했을 때 저장 실패로 표시하거나 다시 저장하지 않는다. 목록의 변경 버튼을 잠시 막고 **목록 다시 불러오기**만 제공한다.
- `VERSION_CONFLICT` 또는 404에는 이전 편집 대상·시도를 폐기하고 목록을 다시 조회하여 재선택하도록 안내한다. 버전이 없는 대상은 수정·삭제 요청을 보내지 않는다.
- `CATEGORY_NAME_EXISTS`의 서버 message는 이름 입력란 아래에 표시하고 입력란을 오류 상태로 표시한다. 이름을 변경하면 해당 오류를 해제한다.
- 변경 요청 또는 후속 목록 조회의 403에는 서버 안내를 표시하고 카테고리 관리 폼·작업 버튼을 숨긴다. `CATEGORY_IN_USE`, 입력 오류 및 요청 ID는 API 오류 안내를 유지한다. 사용 중인 카테고리를 로컬에서 강제로 삭제하지 않는다.
- 요청 진행 중에는 중복 제출·창 닫기를 막는다. 관리 화면 종료나 계정 변경 뒤 늦게 완료된 요청은 새 계정 목록을 갱신하지 않는다.
- 카테고리 관리 후 서버·관리자/일반 분류 목록을 다시 읽어 서버 추가·수정 선택지에 반영한다. 조회 실패는 상위 화면과 관리 모달에서 처리할 수 있도록 전달한다.
- 서버 현황의 카테고리 이름은 최신 분류 목록을 우선하여, 예전에 서버 객체에 저장했던 이름이 수정된 이름을 덮지 않도록 했다.

삭제는 백엔드의 논리 삭제다. 활성 서버가 참조하면 409 CATEGORY_IN_USE이며, 삭제 처리된 서버·과거 대여 이력은 보존된다.

## 검증 범위

- 카테고리 전용 자동 검사 12개: 실제 API 클라이언트의 메서드·경로·Bearer·JSON·버전·멱등 키·204 처리와 오류 전달, 실제 JSX 콜백의 입력 검증·중복 제출 방지·재시도·충돌·삭제 확인·목록 재조회 실패·계정 변경을 검사했다. 이름 입력란 오류·기존 설명 유지/삭제·키 재사용 오류 뒤 새 키·403 작업 차단도 포함한다.
- UI 콜백 시험은 Babel로 실제 컴포넌트를 읽고 결정적 hook 환경에서 실행했다. 실제 브라우저 레이아웃이나 실행 서버에 대한 E2E 시험은 아니다.
- 전체 프론트 자동 시험은 **132개 통과**했다. 실서비스 데이터 대신 시험 응답을 사용하는 오프라인 검사다.
- 웹 production export 성공. 기존 정적 미리보기에서 새로고침하면 새 빌드가 반영된다. 백엔드/API 주소는 이번 변경에서 바꾸지 않았다.
- 현재 프론트의 아이디·비밀번호 로그인은 그대로이며 SE 게시판 로그인 전환 요청 문서는 별도다. 카테고리 연동 작업에서 인증 방식을 임의 변경하지 않았다.
- **실행 중인 백엔드에 로그인하여 카테고리를 등록·수정·삭제하는 시험은 아직 수행하지 않았다.** 실제 API 주소와 서버에서 ADMIN으로 확인되는 계정으로 아래 절차를 확인해야 한다. 실제 토큰·암호는 이 문서에 기록하지 않는다.

## 실제 환경 확인 순서

1. 실제 API 주소로 로그인하여 `/api/v1/me`가 ADMIN을 반환하는지 확인한다.
2. 관리자 카테고리 관리에서 미배정 카테고리까지 조회되는지 확인한다.
3. 겹치지 않는 시험용 이름으로 하나를 추가하고 관리자 목록·서버 추가 폼에서 확인한다.
4. 이름·설명을 수정하고 최신 version·서버 행의 표시명 갱신을 확인한다.
5. 동일 이름 충돌, 다른 창의 수정에 따른 버전 충돌, 연결된 활성 서버의 삭제 제한을 확인한다.
6. 서버에 연결하지 않은 시험 분류를 삭제하고 204·목록 제거를 확인한다. 취소 시에는 DELETE가 전송되지 않아야 한다.
7. 테스트 계정에서 관리자 API 403이 정상 동작하는지 확인한다.
8. 저장 성공 뒤 목록 통신만 실패했을 때 저장 재전송 없이 목록 조회만 재시도하는지 확인한다.

이 문서와 시험 통과가 SE 인증 연동, 실제 DB 마이그레이션 적용, Proxmox VM 생성·반납까지 검증했다는 의미는 아니다.
