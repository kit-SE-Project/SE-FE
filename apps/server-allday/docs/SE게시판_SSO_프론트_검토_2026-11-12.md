## 머지 전 보완 사항

### 1. [P1] 쿠키의 사용자가 바뀌었을 때 이전 계정의 화면 상태를 폐기해야 함

- 위치: 대여 웹 `App.jsx:123–140`.
- 다른 탭에서 같은 대여 사이트에 B 계정으로 SSO 로그인하면 호스트 쿠키는 탭들이 공유하므로 A 탭의 다음 `/api/v1/me`도 B를 반환할 수 있다.
- 현재 비교에는 `memberId`가 없어서 두 계정의 역할·대여 자격이 같으면 `actor`를 교체하지 않는다. 추가 검사에서 `/me`의 `memberId=99`에도 헤더는 기존 `memberId=83`을 유지했다.
- 이후 목록 요청은 새 쿠키를 사용하므로 기존 사용자 표시와 새 사용자의 대여 목록이 섞인다. 기존 선택·확인 모달·접속 정보 등도 계정 전환 기준으로 초기화되지 않는다.
- 수정 방향: `memberId` 변경을 권한 변경과 구분해 처리한다. 이전 client의 진행 중 응답을 무효화하고, 계정별 화면 상태·캐시를 지운 뒤 새 사용자 기준으로 목록을 다시 읽는다. 역할이 같다는 이유로 동일 계정으로 취급하지 않는다.
- 이 결과는 프론트 계정 분리 문제이며 백엔드 권한 우회가 입증됐다는 뜻은 아니다.

### 2. [P2] 로그아웃 응답이 끊기고 재확인이 비로그인을 반환해도 이전 화면이 남음

- 위치: 대여 웹 `App.jsx:89–106`, `174–185`.
- 재현: 서버는 로그아웃을 완료했지만 응답을 받지 못함 → 로그아웃 catch에서 복원을 다시 시도 → `/me`가 401이어서 `restoreSsoSession()`이 null 반환.
- null 분기는 안내와 `restoring`만 갱신하며 기존 `actor`, `api`, 대여 목록을 지우지 않는다. 추가 검사에서 로그인 화면 대신 기존 회원의 헤더가 계속 표시됐다. 실제 API 클라이언트의 null 복원 동작과 앱의 null 분기를 각각 확인했다.
- 수정 방향: 재확인 결과가 비로그인일 때는 `clearLocalSession()` 등으로 계정·목록·열린 모달을 폐기한다. 비로그인이 확인된 뒤 과거 세션 만료 처리 때문에 자동 SSO가 다시 시작되지 않도록 로그아웃 의도를 유지한다.
- 재확인에서 503이면 세션이 종료됐다고 단정하지 말고 오류와 재시도 방법을 표시한다.

### 3. [P2] 기존 세션이 유효하면 SSO 콜백 실패 안내를 건너뜀

- 위치: 대여 웹 `App.jsx:89–100`.
- 재현: 기존 대여 쿠키가 유효한 상태에서 새 로그인 요청의 콜백이 실패하여 `/?sso=unavailable` 또는 `/?sso=expired`로 돌아옴.
- `/me`가 성공하면 `activateSession()`으로 바로 진입하고, URL 처리 코드는 session이 null인 분기 안에 있어 실행되지 않는다. 추가 검사에서 화면에 로그인 실패 안내가 없고 쿼리도 남았다.
- 수정 방향: SSO 결과 쿼리를 세션 복원 성공 여부와 독립적으로 한 번 읽고 제거한다. 유효한 기존 세션을 유지하더라도 새 인증 요청 실패를 명확히 안내한다.

### 4. [P2] 늦게 도착한 만료 응답이 게시판 refresh를 다시 실행함

- 위치: SE-FE `apps/se-board/src/api/axiosInstance.ts:86–99`.
- 여러 요청이 같은 만료 access token을 사용했을 때 첫 오류가 토큰 갱신을 완료한 후 다른 요청의 만료 응답이 도착할 수 있다.
- 현재 코드는 해당 요청이 사용한 access token과 현재 저장된 access token을 비교하지 않고 `refreshStoredAccessToken()`을 다시 실행한다. 진행 중 refresh를 공유하는 검사는 통과했으나, 지연 응답 검사에서는 refresh가 2회 실행됐다.
- 수정 방향: 만료 응답의 원래 Authorization이 현재 저장된 access token과 다르면 이미 갱신된 토큰으로 한 번 재시도한다. 아직 같은 토큰일 때만 공통 refresh를 시작/공유한다. 재시도 제한과 계정 변경 검사는 유지한다.
- 이는 “동시에 만료돼도 갱신은 1번”이라는 검수 조건의 미충족 사례다. 이전 인터셉터에도 비슷한 경계 조건이 있을 수 있으므로 신규 변경에서만 처음 발생한 문제라고 단정하지 않는다.

## 검사 결과와 제한

- 검토 브랜치 원본의 `node --test tests/*.test.cjs`: **122개 통과**. 기존 데모 인증과 추가된 SSO API 검사 2개 포함.
- 보조 검사 `.local-only/sso-review-2026-11-12/review.test.cjs`: **8개 검사 완료**. 실제 App JSX의 콜백과 실제 게시판 TypeScript 인터셉터를 실행하되 React hook, 네트워크 응답·시간, 저장소 및 axios 전송 어댑터는 제어했다. 위 4개 문제의 재현과 정상 동작 4개를 확인했다. 검사 통과는 문제를 수정했다는 의미가 아니다.
- 설치된 의존성과 검토 브랜치 lockfile은 JSON 내용·패키지 버전이 동일하다. 빌드용 의존성을 재설치하지 않고 별도 복사본에서 재사용했다.
- 검토 복사본에서 `EXPO_PUBLIC_SEBOARD_SSO_ENABLED=true`, `EXPO_OFFLINE=1`로 실행한 `npm run build:web` 성공. 기존 실행용 `dist`는 교체하지 않았다.
- 배포된 양 사이트를 이용하는 브라우저 E2E, 실제 쿠키·프록시·Redis·DB·카카오 로그인, 게시판 전체 테스트/전체 빌드는 이번 검증에 포함하지 않는다.
- 원본 작업 폴더에서 앞서 보완한 카테고리 변경은 아직 미커밋이며 SSO 커밋 `84c9c8b`에는 포함되어 있지 않다. 후속 통합 시 함께 보존해야 한다.

## 실제 환경 최소 검수

1. 대여 웹 운영 빌드에 SSO를 켜고 웹과 `/api/v1`을 같은 HTTPS 오리진으로 프록시한다. 기존 정적 미리보기 서버는 API 프록시가 없어 이 설정만 켜면 SSO를 실행할 수 없다.
2. SE 웹에 `REACT_APP_ALLDAY_ORIGIN`, 양 백엔드에 콜백·공유 비밀·공개 오리진·게시판 내부 주소를 맞춘다. 공유 비밀은 프론트 빌드 변수에 넣지 않는다.
3. SE 비로그인 → SE 로그인 → 대여 복귀, SE 로그인 상태 → 추가 입력 없이 대여 복귀를 확인한다. 일반 로그인과 카카오 로그인을 각각 검사한다.
4. Network에서 대여 API에 쿠키가 전송되고 Bearer가 없는지, 변경 요청의 Origin이 허용되는지 확인한다.
5. 권한 변경·SE 로그아웃·계정 탈퇴·대여 8시간 만료를 확인한다. 30초는 백엔드 캐시 상한이며 현재 프론트의 표시 갱신 주기와 동일하지 않다. 백그라운드 탭은 복귀 시 갱신한다.
6. 401 재로그인, 503 세션 유지·오류 안내, 로그아웃 204, 응답 손실 뒤 비로그인 재확인을 검사한다.
7. 두 탭에서 A/B 계정을 전환해 이전 대여·접속 정보·확인 모달이 남지 않는지 확인한다.
8. 게시판 일반 화면에서 access 만료, refresh 만료, 동시에 실패하는 요청, 갱신 뒤 늦은 만료 응답을 각각 검사한다.
9. 서버에 연결되지 않은 카테고리를 관리자 목록에서 확인하고 추가·수정·삭제 및 버전 충돌을 확인한다.

게시판의 공통 JWT/refresh 수정은 게시판 전체 로그인에 영향을 주므로 SSO 연결 변경과 검토 단위를 나누는 방향이 적절하다. 단, SSO 브랜치가 해당 수정에 의존하므로 분리하더라도 적용 순서와 필요한 선행 커밋을 함께 명시해야 한다.
